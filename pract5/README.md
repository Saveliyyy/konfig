# Практическое занятие №5 — ассемблер и интерпретатор УВМ

Решены все три задачи (варианта). Каждая лежит в своей папке и не зависит от других.

| Папка | Машина | Операция | Синтаксис ассемблера | Дамп памяти |
|---|---|---|---|---|
| `task1/` | регистровая, 128 регистров | `abs()` | текстовый | XML |
| `task2/` | стековая | `pow()` | JSON | CSV |
| `task3/` | аккумуляторная | `sgn()` | CSV | JSON |

Требуется только Python 3.9+, сторонние библиотеки не нужны.

## Состав каждой папки

| Файл | Назначение |
|---|---|
| `isa.py` | Спецификация команд (коды, поля, биты), кодирование и декодирование |
| `assembler.py` | Ассемблер: этапы 1 и 2 |
| `interpreter.py` | Интерпретатор с дампом памяти: этапы 3–5 |
| `run_all.py` | Прогон всех этапов одной командой |
| `programs/test.*` | Тесты из спецификации, воспроизводят все тестовые байты (этапы 1–2) |
| `programs/copy.*` | Копирование массива (этап 3) |
| `programs/alu.*` | Проверка операции АЛУ (этап 4) |
| `programs/vector.*` | Основная тестовая задача (этап 5) |
| `programs/example1..3.*` | Ещё три примера к этапу 5 |
| `out/` | Уже полученные `.bin` и дампы памяти |

## Быстрый запуск

```
cd task1
python run_all.py
```
Выведет тестовые поля и байты, размеры бинарников и создаст дампы в `out/`.

## Ручной запуск

Ассемблер (одинаково во всех вариантах):
```
python assembler.py <исходник> <программа.bin> [--test]
```
С флагом `--test` печатаются промежуточное представление (`A=26, B=28, C=43`)
и байты каждой команды (`0x1A, 0x67, 0x05, ...`). Размер файла печатается всегда.

Интерпретатор:
```
python interpreter.py <программа.bin> <файл дампа> <начало>:<конец>
```
Пример для варианта 1:
```
python assembler.py programs/vector.asm out/vector.bin
python interpreter.py out/vector.bin out/vector.xml 300:317
```

## Модель памяти

Память команд и данных объединена: 1024 ячейки, программа загружается с адреса 0,
по одному байту кода на ячейку. Данные лежат в той же памяти после кода
(вариант 1 — с адреса 300, варианты 2 и 3 — с адреса 200).
Выполнение идёт до конца программы.

## Синтаксис и семантика

### Вариант 1 (`task1/programs/*.asm`), `;` — комментарий
```
load_const B, C      ; reg[B] = C
read       B, C      ; reg[B] = mem[reg[C]]
write      B, C, D   ; mem[reg[C] + B] = reg[D]
abs        B, C      ; mem[reg[B]] = abs(reg[C])
```
Вектор `300..307` → новый вектор `310..317`.

### Вариант 2 (`task2/programs/*.json`), ключ `comment` игнорируется
```
{"op": "load_const", "B": 38}     push(B)
{"op": "read", "B": 309}          push(mem[B])
{"op": "write"}                   value = pop(); addr = pop(); mem[addr] = value
{"op": "pow", "B": 180, "C": 1}   x = pop(); base = pop(); mem[base+B] = pow(x, mem[base+C])
```
Вектор `200..207`, число 153 в ячейке `210`, результат на месте.

### Вариант 3 (`task3/programs/*.csv`), строки на `#` — комментарии
```
op,B,comment
load_const,635      acc = B
read,517            acc = mem[acc + B]
write,32            mem[B] = acc
sgn,739             acc = sgn(mem[B])
```
Вектор `200..204`, результат на месте.

## Допущения

В спецификации не уточнено несколько деталей, их я выбрал так:
- Порядок снятия со стека в варианте 2: первым снимается значение (верх стека), затем адрес.
  То есть перед `write` и `pow` сначала кладётся адрес, потом значение.
- Константы в `load_const` вариантов 1 и 3 знаковые (дополнительный код в пределах поля).
  Иначе в память нельзя положить отрицательные числа для `abs()` и `sgn()`.
  На тестовые байты это не влияет.
- В варианте 2 константа 8-битная (0..255), поэтому данные лежат по адресам меньше 256.
